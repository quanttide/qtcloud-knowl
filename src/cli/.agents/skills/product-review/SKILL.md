# Product Review Checklist

我反复犯过以下错误。每次评审前逐条检查，**不默念、不跳过**。

## 1. 命名：用户怎么叫它？

- [ ] 这个命名用户第一次见到能猜出意思吗？
- [ ] 还是只有工程师才懂？（反例：`formal`、`new`、`simple`）
- [ ] **测试**：把名字念给非技术同事听，看他能不能解释

## 2. 输出：用户看懂了吗？

- [ ] 输出的每一行，用户都知道它是什么意思吗？
- [ ] 有没有暴露技术术语？（反例：`检测到 3 个未抽象信号`、`跨领域关系覆盖率`）
- [ ] 用户看到报告后知道**自己该做什么**吗？
- [ ] **反例复盘**：v0.0.6 的 audit 输出了工具名和检测结果，业务专家看不懂

## 3. 错误：用户知道接下来怎么办吗？

- [ ] 出错时给的是业务语言还是一堆 traceback？
- [ ] 错误消息包含**原因 + 下一步**，还是只有原因？
- [ ] **反例复盘**：data_home 设成不存在的路径时疯狂报 `PermissionError` 而不是"请确认目录路径"

## 4. 引导：用户知道怎么用下一步吗？

- [ ] 新功能有没有告诉用户"什么时候该用它"？
- [ ] 有没有告诉用户"用了之后下一步做什么"？
- [ ] **反例复盘**：v0.0.8 的 `--mode new` 跑完后用户不知道还可以跑 `--mode formal`

## 5. 成功：用户知道一切正常吗？

- [ ] 全部通过时有正向确认信号吗？还是什么都不输出？
- [ ] **反例复盘**：早期 audit 全部通过时只返回 0，用户不知道是"没跑"还是"全过了"

## 6. 信息量：用户看到的信息够做决策吗？

- [ ] 报告除了指出问题，还告诉用户怎么修了吗？
- [ ] 每个问题都指向具体文件路径和字段了吗？
- [ ] **反例复盘**：v0.0.6 的 audit 报告只说"有问题"，不说"改哪个文件"

## 7. 心智模型：用户的理解和实现一致吗？

- [ ] 用户可能会怎么理解这个功能？和实际行为一致吗？
- [ ] 有没有可能用户理解错了但系统没有提示？
- [ ] **反例复盘**：`extract` 名字让用户以为能自动抽取本体实例，实际只创建了骨架

## 8. 文档：写之前先确认代码是真的

- [ ] 文档描述的功能**代码里真的有吗**？还是计划中的？
- [ ] **反例复盘**：v0.0.6 的 extract 文档写了"自动抽取本体实例"，实际 extract 还没接 LLM，骨架都没建全

## 9. 文档：一份就够了，不要拆

- [ ] 是不是写了一堆小文档，而不是一份完整的？
- [ ] 用户需要看几份文档才能理解全部？**目标：一份**
- [ ] **反例复盘**：同一件事写了 `overview.md`（业务版）和 `index.md`（技术版），用户不知道该看哪个

## 10. 文档：写完后检查引用是否断裂

- [ ] 文档里引用的其他文件路径还存在吗？
- [ ] 文档目录结构变了吗？引用更新了吗？
- [ ] **反例复盘**：docs 从 `src/cli/docs/` 移到顶层 `docs/` 后，test_docs.py 的 `DOCS_DIR` 路径没更新，测试挂了

## 11. 文档：写完代码立刻同步，不积压

- [ ] 代码改完那一步，相关文档同步了吗？还是等"最后一起写"？
- [ ] **反例复盘**：多次出现代码改完后忘记更新 STATUS.md 和 README.md，到提交前才补

## 12. CLI 设计标准

- [ ] **渐进式暴露**：用户第一眼只看到 2 个命令，高级功能隐藏但不删除
- [ ] **合理默认值**：所有选项都有安全的默认值，用户不加参数也能跑
- [ ] **一致退出码**：0=成功，1=用户级错误，不混淆
- [ ] **`--help` 说人话**：描述用业务语言，包含子检测/子流程的展开说明
- [ ] **`--verbose` / `--quiet`**：默认只输出用户关心的，详情用 `--verbose` 控制
- [ ] **无副作用**：不修改用户数据（audit 只读），修改用户数据前告知
- [ ] **可消费的输出**：报告既有给人读的格式，也有给机器读的格式（备选：`--json` / `--format`）
- [ ] **环境变量 > 配置文件**：配置通过 env var 传入，不依赖配置文件路径（参考 gh 的 `GITHUB_TOKEN`）
- [ ] **反例复盘**：v0.0.6 的 audit 没有增量对比和 `--verbose`，用户每次看到完整输出，不知道什么变了

## 13. CLI 文档标准：参考 gh 手册结构

每条命令的文档应包含以下要素，按顺序：

```
命令签名 — 命令 + [flags]
一句话说明 — 这个命令做什么
关键行为 — 边缘情况、用户需知的约定（要点列表）
选项 — 参数表格（名称、类型、说明）
示例 — 2-3 个实用的一行命令
实际输出 — 用户运行命令后看到的终端输出
```

- [ ] 每条命令有一句话说明（参考 gh：`gh pr create` → "Create a pull request on GitHub."）
- [ ] 有"实际输出"块展示终端内容（参考 gh：In use 章节）
- [ ] 有示例（参考 gh：Examples 章节）
- [ ] 选项用表格列出来，不散在段落里
- [ ] **反例复盘**：我们的 docs/index.md 有命令说明但没有实际输出示例，用户不知道运行后会看到什么
