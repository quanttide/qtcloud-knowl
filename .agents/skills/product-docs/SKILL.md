# Product Docs Skill

业务人员的文档不是技术手册。他们不需要知道实现细节，他们需要知道：这个工具能帮我做什么、怎么开始、出了问题怎么办。

## 文档分层

```
产品文档（docs/）              → 业务人员阅读：what & why
CLI 参考（src/cli/docs/）      → 操作者阅读：how
README                         → 新用户第一眼：快速开始
AGENTS.md/TODO.md              → 内部执行记录，不面向用户
```

产品文档和 CLI 参考分开维护，不要混在一起。

## 产品文档（docs/）每篇的职责

| 文档 | 回答的问题 | 语气 |
|------|-----------|------|
| index.md | 这是什么工具？它解决什么问题？ | 产品介绍 |
| contract.md | 人和 AI 分别负责什么？ | 分工说明 |
| criteria.md | 什么样的结果是好的？ | 质量标准 |
| workflow.md | 完整流程是怎样的？ | 流程说明 |
| storage.md | 我的数据存在哪？ | 配置参考 |

## 写作原则

**先说什么，再解释为什么。** 第一段应该让读者知道这篇文章和他有什么关系。

**一个文档只回答一个问题。** 如果读者需要跳转才能理解，说明拆分不对。

**用读者的语言，不是工程师的语言。** "本体抽象度检测"在面向业务人员时应该说"检查知识结构是否通用"。

**每个命令给出业务场景，不只是语法。** 不是"`review --list` 列出待审项"，而是"你每周一可以用 `review --list` 查看本周需要评审的知识条目"。

## 检验标准

- 业务人员读完知道自己该做什么吗？
- 一篇文档可以独立阅读，不需要先读另一篇吗？
- 出问题时文档能告诉他去哪里看吗？
- 文档里的命令名和实际 CLI 一致吗？（不一致的要在产品文档里做说明或省略）

## 反例

- 产品文档里写 CLI 命令的详细参数列表（那是 CLI 参考的事）
- CLI 参考里写产品愿景（用户只想知道怎么用）
- 文档从对话记录开始（"你说得对。它是一个知识工程工具……"）
- 把设计过程中的备选方案写进文档（"这个工具的正式名称可以是……"）
