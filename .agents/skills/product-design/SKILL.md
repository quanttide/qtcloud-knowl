# Product Design Skill

反思来自 `qtcloud-knowl` CLI 在 v0.0.5~v0.0.14 期间过度打磨 UX 和代码卫生，平台核心链路（LLM 抽取）从未启动的经验。

## 核心原则

**版本交付的不是功能，是用户能力。** 每个版本完成后，用户应能做一件之前做不到的事。

## 价值分层

| 层 | 定义 | 投入上限 |
|----|------|---------|
| **核心链路** | 平台存在的理由，用户为它而来 | 无限 |
| **可用性** | 核心链路能跑通但不优雅 | 核心链路没跑通前不做 |
| **代码卫生** | 重构、去重、类型修复 | 核心链路没跑通前只修 block 级别的 |
| **流程基建** | ROADMAP、CHANGELOG、skills | 做到不迷路的程度就停 |
| **边缘打磨** | 输出措辞、默认模式、颜色、补全 | v0.1.0 之后再考虑 |

## 自检清单（每次开工前）

1. 这个版本解决的用户痛点，是核心链路的一环还是边缘？
2. 做完这件事，用户能做一件之前做不到的事吗？
3. 如果版本是自行提议的（非用户要求），先问再做
4. 当前是第几次在非核心链路上迭代了？如果是第 3+ 次，停下来

## 从实践中吸收的经验

### 做对了的

**痛点优先而非功能优先** — 每个版本的第一行是"痛点：xxx"，不是"新增：xxx"。v0.0.11 写的是"审计结果不可靠"，不是"新增 hash-based diff"。这保证版本目标始终以用户视角定义。

**敢于推迟** — LLM 抽取在 v0.0.10 就规划了，但一直推迟到 v0.1.0。理由明确：没人用就没有需求，没有 TODO 分解就不值得估算。推迟不是忘记，是主动选择。

**被叫停时不辩护** — 当说"版本分解过细致了"，立刻合并 4→2，不解释为什么细致有道理。好的产品经理听信号比说理由重要。

**评审标准是用户行为，不是代码行为** — product-review 的 13 项检查点，每一项都是用户侧的（命名猜得出吗？输出看得懂吗？知道下一步做什么吗？），没有一条是代码侧的。

### 可以吸收的

**用"用户多了一项什么能力"检验每个版本** — v0.0.11 之前每个版本都能明确回答（audit 能用了、输出可读了、diff 可比较了）。v0.0.12 之后回答开始模糊（"代码更干净了"）。当回答变成技术好处而非用户好处时，版本规划出了问题。

**三个信号判断技术债是否值得现在修**：
1. 重复代码是否有细微差异导致 bug？（`Instance.data` 一个 `{}` 一个 `Field(default_factory=dict)`）→ 值得修
2. 重复代码是否会拖慢下一个核心功能的交付？→ 值得修  
3. 只是看着不顺眼？→ 不值得修

v0.0.12 的 SDK 抽取满足 1+2，所以是对的；v0.0.8~v0.0.10 的大部分抛光不满足任何一条，所以是过度。

**版本粒度原则**：一个版本 = 用户感知得到的一个变化。如果拆开来用户感觉不到差别（如"改了输出措辞"和"改了默认模式"是两个版本），说明拆太细了。
