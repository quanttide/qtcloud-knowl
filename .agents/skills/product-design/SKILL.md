# Product Design Skill

反思来自 `qtcloud-knowl` CLI v0.0.5~v0.0.12 期间过度打磨，以及后续将 LLM 抽取拆解为 v0.0.13~v0.1.0 的经验。

## 核心原则

**版本交付的不是功能，是用户能力。** 每个版本完成后，用户应能做一件之前做不到的事。

## ROADMAP 设计流程

### Step 1: 定义终点（v0.1.0 / 下一次里程碑）

用户最终能做什么事？例如：文档直接变成知识库，经审核后发布。

### Step 2: 从终点倒推，用户缺少什么能力？

列出从今天到终点之间的缺失环节，每项是用户感知得到的一个能力缺口：

| 缺失环节 | 用户缺什么 |
|----------|-----------|
| 看不到 LLM 抽出了什么 | 无法验证 prompt 效果 |
| 没法保存抽取结果 | 无法对比迭代 |
| 不能审核确认 | LLM 结果无法落库 |

### Step 3: 每个缺失环节拆成一个版本

按依赖顺序排列，确保每个版本单独给用户带来可感知的价值。**不要为了技术解耦拆分版本，要为"用户多了什么能力"拆分。**

### Step 4: 用"用户能力"校验每个版本

问自己：这个版本做完，用户能做之前做不到的一件事吗？如果答案是"代码更干净了"或"体验更好了"，说明这不是一个版本，是一次重构或抛光。

## 版本粒度口诀

- ❌ 一个版本 = 一个技术重构（SDK 抽取、删重复代码）
- ❌ 一个版本 = 一次体验优化（改默认模式、调措辞）
- ✅ 一个版本 = 用户多了一项能力

## 版本范围检查

- 这个版本做得完吗？（单次迭代 1~2 天，需要持续验证的不可一次提交）
- 如果版本跨度太大，中间再插一个用户可见的中间态

## TODO 分解经验

每个版本确定后，按以下规则拆 TODO：

1. **每条 task 有停止条件** — 不是"实现 X 功能"，而是"什么算做完"。反例："实现 LLM 调用"；正例："extract --llm 读取文档后返回原始 LLM 输出到 stdout"

2. **停止条件可被测试验证** — 如果写不出停止条件，说明 task 定义不够具体，需要继续拆

3. **每条 task 可独立完成** — 不能出现"做 A 之前必须做 B，做 B 之前必须做 A"的循环依赖

4. **tests 和 docs 必须是单独的 task** — 不嵌入功能 task，否则会被跳过。每个版本至少有一条 "tests" 和一条 "docs" task，确保覆盖率和文档同步。反例：停止条件写"含测试"但从未执行；正例：独立的 `[ ] tests（覆盖 X/Y/Z 场景）` 和 `[ ] 更新 CHANGELOG + docs/commands.md`

5. **版本停止条件 = 用户新能力的可操作描述** — 问：怎么证明这个版本做完了？打开终端跑什么命令、看到什么输出，证明用户能做之前做不到的事

## 版本完成后的清理

每个版本发布后，立即执行以下清理，否则 ROADMAP 和 TODO 会随时间膨胀到无法维护：

1. **ROADMAP：已发布的版本只保留痛点摘要，不保留解决细节** — 细节已记录到 CHANGELOG。ROADMAP 是前瞻工具，不是历史档案
2. **TODO：整个版本节标记为 [已发布]**，所有 task 标 `[x]`，或移动到下一版本
3. **不保留"待清理"或"以后再说"的残留 task** — 要么做完，要么正式推迟到规划中的版本，否则删除
4. **CHANGELOG 必须在发布前更新**，作为版本完成的最终确认步骤

反例：v0.0.12 发布后 ROADMAP 仍保留 v0.0.12 的完整痛点/解决描述（占 5 行），v0.0.11 也保留着。ROADMAP 一半篇幅是已完成内容，干扰视线。

## 经验：如何设计 v0.0.x 到 v0.1.0 的过渡

从 ROADMAP 实践中总结：

1. **先定义终点能力**（v0.1.0 的能力描述），再倒推出中间版本
2. **中间版本不必是技术架构步骤**，而是依次解锁的用户能力：看到 LLM 输出 → 保存结果 → 审核确认 → 全链路闭环
3. **每个中间版本单独有价值**，不是只有 v0.1.0 才有用
4. **我被叫停时立刻调整**，不辩解（版本拆太细就合并，缺少环节就补充）
